# 选题二：验证与评测负责人交付工作单

适用项目：全国大学生嵌入式芯片与系统设计竞赛 2026 FPGA 赛道，中科亿海微，选题二“多路选择器 PMUX 结构优化”。

本文可以直接交给队友的 Codex，作为该侧工作的任务入口。当前项目只有赛题 PDF，尚未建立代码仓库、开发环境、优化插件或官方测试基准。下面的目录、命令和接口均为拟定协作约定，不代表已经实现。

## 1. 你的职责与最终目标

你是验证与评测负责人，Codex 是你的主要实现助手。你的最终成果是一套其他人能复现的测试与评测系统，能回答：优化结果是否等价、资源减少多少、运行时间及峰值内存多少、结果如何复现。

主开发侧负责 C++ 优化插件、算法和 Tcl 调用入口。你侧负责独立测试、EQY 配置、评测脚本、结果分析和官方要求核对。双方共同确定评测口径和工具版本。

你本人负责获取官方资料、确认规则、复核实验结论，并掌握答辩内容。Codex 负责实现脚本、生成测试、安装调试工具、分析日志和起草报告。所有成果必须基于实际运行记录，不能用推测填补实验结果。

## 3. 环境准备

推荐 Windows + WSL2 Ubuntu，工具版本由双方统一固定。先检测已有环境，再安装缺失项，避免重复配置或覆盖已有环境。

需要的工具：Git、Python 3、Yosys、EQY、SBY、实际选用的形式验证求解器，以及 GNU time。推荐使用 OSS CAD Suite 提供综合及形式工具；插件编译环境由主开发侧确定。验证侧只有在需要编译收到的插件时才补齐匹配的构建环境。

官方入口：

- WSL：https://learn.microsoft.com/zh-cn/windows/wsl/install
- OSS CAD Suite：https://github.com/YosysHQ/oss-cad-suite-build
- 发布包：https://github.com/YosysHQ/oss-cad-suite-build/releases
- EQY：https://yosyshq.readthedocs.io/projects/eqy/en/latest/

安装时查询官方当前说明，并记录准确版本或提交号及安装包来源。不要仅写“最新版”。不要假设任意版本插件二进制能与任意版本 Yosys 兼容。

环境验收：

1. Yosys 能读取并综合一个简单 Verilog 组合电路。
2. EQY 对已知等价的一对设计返回通过。
3. EQY 对故意改错的一对设计返回失败，日志可以定位结果。
4. Python 能启动工具、取得退出码、保存标准输出和错误输出。
5. 记录操作系统、WSL 情况、CPU、内存、工具版本及实际调用路径。

遇到管理员操作、系统重启或网络阻断时，记录准确阻塞点；继续完成不依赖该步骤的测试设计和文档，不把未执行步骤写成已完成。

## 6. 工作包 A：建立独立测试集

先交付不少于 12 个有明确设计意图的确定性案例，再增加参数化和随机案例。数量不能代替覆盖率。

至少覆盖以下类型：

1. 单级 PMUX：不同数据位宽与分支数。
2. 重复数据分支：验证分支合并相关行为。
3. 常量数据分支：全零、全一及混合常量。
4. 默认输入与部分分支数据相同。
5. 选择信号包含常量或相互关联的逻辑。
6. 嵌套或级联选择结构。
7. PMUX 前后混合与、或、异或及其他组合逻辑。
8. 多输出共享逻辑，防止改写影响其他使用者。
9. 无 PMUX 的控制案例，验证工具不会误处理。
10. 位宽为 1、窄位宽、较宽数据、多分支等边界。
11. 不应产生优化收益的控制案例，检查报告是否如实显示零收益或退化。
12. 接近规模限制的压力案例，实际统计节点数，不能凭源码行数推定。

每个案例记录 id、源文件、top、参数、类别、设计意图、期望是否产生 PMUX、约束、随机种子和适用范围。约束必须来自电路结构或经确认的规范，不能为让验证通过而随意添加。

关键检查：Verilog 中写了 `case` 不代表综合后一定产生 `$pmux`。应在插件插入点检查实际单元类型和数量。必要时用 RTLIL 精确构造单元级测试，但将其与源级测试分别汇报。

先查看固定版本 Yosys 中 `$pmux` 的定义，再设计多路同时选中和未定义值案例。不要将它任意解释成优先级 MUX，也不要用未经证明的 one-hot 假设改变定义域。必要的假设必须进入报告及 EQY 配置并与主开发侧确认。

随机测试保存种子和生成参数。优先采用“同一生成器、不同参数和逻辑结构”，避免只生成重复分支等天然有利于算法的案例。保留一组不参与调参的回归案例，并记录其用途。

## 7. 工作包 B：建立形式等价验证

以 EQY 为比赛验证主流程；仿真可用于调试，但不能替代形式验证结论。

对每个案例生成 golden 与 revised，保存完整脚本和日志。根据官方口径选择验证端点；开发期间至少检查插件前后结果，最终还应检查完整候选流程的端到端结果。

必须区分以下状态：

- PASS：工具明确证明通过，所有必要分区均已完成。
- FAIL：发现不等价。
- UNKNOWN：未完成证明或结果不确定。
- TIMEOUT：超过指定限制。
- ERROR：工具缺失、配置错误、解析失败、进程异常等。
- SKIP：因已说明的条件未执行。

只有 PASS 可以计入“全部等价通过”。不能只依据进程退出码或日志里出现某个 PASS 字样；应结合固定版本 EQY 的最终状态和分区结果判断。

至少增加一个人工引入错误的负向自测，证明验证系统确实能拒绝错误结果。该负向自测不进入优化成功率统计。

出现失败时交付：最小可复现输入、工具版本、完整执行命令、候选插件提交号、日志、反例文件（若工具生成）、初步归因。失败案例保留进回归集。

## 8. 工作包 C：建立资源与性能评测

对同一个案例，基准和候选必须使用同一工具版本、输入、顶层、参数、映射目标及共同的后处理流程。所有流程保存为文件并记录版本。

资源减少率：`(baseline_cells - optimized_cells) / baseline_cells * 100%`。当基准 cell 数为零时记为 N/A。结果为负值时如实报告退化。

分别记录插件前后中间网表数据，以及完整综合流程结束后的数据。不要把单个宽位宽 `$pmux` 的消失直接称为面积下降；不同层级的 cell 数不能混合比较。若没有厂商映射环境，结果只能称为对应阶段的 cell 统计，不能称为已经验证的 EQ6HL130P 实际面积收益。

官方聚合方式未确认前，同时展示逐例结果、有效案例优化率均值和总 cell 加权结果，并明确它们只是临时分析口径。不得自行宣称达到官方总分标准。

至少记录：case_id、输入哈希、seed、top、工具版本、基准脚本版本、候选提交号、PMUX 数量、基准 cell 数、候选 cell 数、减少率、等价状态、优化耗时、综合总耗时、EQY 耗时、峰值内存、日志路径。

用外部监测测量时间和内存，不依赖插件自行上报。GNU time 可用于初版测量，但须准确注明其峰值 RSS 的统计范围，不能未经核实就声称是整个并发进程树的总峰值。对进程树设置超时清理，避免超时后求解器仍继续运行。

性能在同一台机器、相近负载下测量。正式对比建议重复 3 次，保留各次值并报告中位数及最差值。插件编译与验证时间单列，待官方确认后决定哪些进入 60 秒指标。未执行或工具不支持的字段用 null/N/A，不能填 0。

报告必须包含全部案例和失败/退化项。未通过等价的案例不进入“有效优化收益”汇总，不得静默丢弃。

## 10. 推进顺序与双方交接

第一阶段：环境、要求记录、集成接口草案。先跑通已知等价和不等价的最小示例。

第二阶段：测试集、identity 全流程、机器可读报告。即使主开发插件未完成，也能独立交付这一阶段。

第三阶段：接入主开发插件，逐例验证，再做完整综合后的资源对比。发现问题提交可复现材料。

第四阶段：补充边界和压力测试，做性能测量，在干净环境复现最终结果，完成报告与答辩说明。

主开发侧应交给你：仓库/代码、提交号、固定工具版本、插件构建与加载命令、Tcl 示例、基准及候选综合脚本、算法适用条件。缺失项明确列出；可以继续做的工作继续推进。

你每完成一个阶段，交给主开发侧：代码提交号或补丁、运行命令、环境记录、结果摘要、原始日志位置、问题列表及下一步依赖。

日常同步只需四项：本次完成内容；实际 PASS/FAIL/UNKNOWN 数量；最重要的失败案例及复现命令；需要对方提供的具体文件或决定。不要只发“报错截图”或“测试通过”。
